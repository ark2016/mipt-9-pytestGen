Материалы для защиты, 13 ноября 2026 года. Qwen2.5-Coder-1.5B-Instruct,
Q4_K_M, CPU, HTTP API llama.cpp. Архитектура и правило предупреждения сохранены.

- [Презентация](../presentation/README.md), [живая демонстрация](../demo.md).
- [Эксперимент](https://github.com/ark2016/mipt-9-pytestGen/actions/runs/43495705978).
- [CI](https://github.com/ark2016/mipt-9-pytestGen/actions/runs/43495706627).
- Измеренный коммит: `c99474b8e3e752768e48ba9d8c98b559faaef604`.
- [Протокол](protocol.md), [все ответы и результаты](results/heuristic-report.json).

Генератор создаёт исполняемые регрессионные тесты, но проход тестов и высокое покрытие
не гарантируют соответствия функции контракту. На контролируемом наборе предупреждение
после repair пропустило единственную успешную подгонку и отметило пять корректных исправлений.
Отдельное LLM-ревью по docstring тоже ненадёжно. Эти результаты не позволяют называть
нынешние предупреждения надёжным детектором ошибок.

## 1. Предупреждение после исправления теста

Правило `is_suspicious_repair`: есть docstring и предшествующее падение похоже
на AssertionError. Оно не анализирует, какую часть assert поменяла модель.
Предупреждение сохраняется между попытками. Неисправленные тесты не записываются
в итоговый файл. В этой работе правило только вынесено в общую функцию для измерения.

Восемь функций, восемь одноточечных мутаций, четыре условия для каждой:
docstring есть/нет × баг в функции/ошибка в тесте. Итого 32 сценария, но восемь
связанных семейств, а не 32 независимых проекта. Не больше двух попыток repair.
Перед моделью pytest проверяет эталон, мутацию и тест-свидетель.

Положительный случай: правильный тест после repair перестал выявлять баг.
Отрицательный: исправлен неправильный тест при правильной реализации.
Матрица включает только проходящие, повторно проверенные содержательные тесты.
Неудавшийся repair не засчитывается как правильно распознанный безопасный случай.

| Условие | Сценариев | Проходящих исправлений | Подгонок | Предупреждений | Не исправлено |
|---|---:|---:|---:|---:|---:|
| Есть docstring, баг | 8 | 0 | 0 | 0 | 8 |
| Есть docstring, ошибка в тесте | 8 | 5 | 0 | 5 | 3 |
| Нет docstring, баг | 8 | 1 | 1 | 0 | 7 |
| Нет docstring, ошибка в тесте | 8 | 5 | 0 | 0 | 3 |
| **Всего** | **32** | **11** | **1** | **5** | **21** |

| Реальное событие | Предупреждение | Нет предупреждения |
|---|---:|---:|
| Подгонка под баг | TP = 0 | FN = 1 |
| Корректное исправление | FP = 5 | TN = 5 |

- Поймано **0 из 1** подгонок. Recall = 0/1; precision = 0/5.
- Ложные срабатывания: **5 из 10** корректных исправлений (FPR 50%).
- С docstring нет успешных подгонок, поэтому recall этой подгруппы **N/A**.
  Все пять её корректных исправлений получили предупреждение.
- Без docstring предупреждение отключено: пять TN, один FN.
- Подгонка случилась в **1 из 16** валидных сценариев с багом. Остальные 15 не доведены
  до прохода; это не 15 правильных решений эвристики.
- Вырожденных проходящих исправлений нет; основная и расширенная матрицы совпадают.

Пропуск: `sum_values/no-doc/bug`. Ожидание `sum_values([]) == 0`
модель заменила на `== 1`, повторяя мутант `sum(values) + 1`.
Тест проходит мутант и падает на эталоне; предупреждения нет.

Ложное срабатывание: `ceil_div/doc/bad-test`. Правильная реализация округляет вверх,
исходный тест ошибочно ожидает `ceil_div(5, 2) == 2`. Модель исправляет ожидание на `3`,
но правило docstring + AssertionError всё равно ставит флаг.
Другие FP: `magnitude`, `occurrences`, `safe_divide`, `sum_values` с docstring.

Все десять успешных исправлений неправильных тестов сохраняют исходный вход и
заменяют ожидание на эталонное. Вручную проверены все 11 проходящих тестов.

## 2. Отдельный LLM-ревьюер

`OracleReviewer` проверяет записанное поведение по docstring; подозрительные
значения исключаются из параметризованных тестов. Здесь 32 наблюдения:
эталон/мутант × docstring есть/нет для тех же восьми функций.

| Выборка | TP | FP | TN | FN | Recall | FPR |
|---|---:|---:|---:|---:|---:|---:|
| 16 выданных оценок, есть docstring | 1 | 1 | 7 | 7 | 12,5% | 12,5% |
| Все 32, отсутствие оценки = нет предупреждения | 1 | 1 | 15 | 15 | 6,25% | 6,25% |

Precision — 1/2. Без docstring все 16 наблюдений UNREVIEWED: восемь ошибок
без предупреждения и восемь правильных наблюдений без предупреждения.
Низкий общий FPR частично объясняется отказом от проверки.

Единственный TP — `safe_divide/doc/mutant`, но его **объяснение неверно**:
модель перепутала обещанное и фактическое поведение. Совпадение флага с разметкой
нельзя считать правильной диагностикой причины.

FP — `reciprocal/doc/reference`: модель спорит с именем функции,
хотя docstring явно задаёт целочисленное деление и исключение при нуле.
Семь остальных документированных мутаций не отмечены. Например,
`ceil_div(5, 2) -> 2` назван согласованным с обещанием округления вверх.

Предупреждение repair оставлено как запрос ручного просмотра. Для более точного
классификатора нужны анализ изменения assert, независимый контракт и новый проверочный
набор. После просмотра результатов текущую выборку нельзя выдавать за независимую
оценку доработанного на ней метода.

## 3. Настоящая библиотека: python-slugify

[python-slugify 8.0.4](https://github.com/un33k/python-slugify/tree/v8.0.4),
ревизия `f85f9488520148d5f6899b5639199882b605e30a`.
Цель — модуль `slugify/slugify.py`, функции `slugify` и `smart_truncate`.
Полный upstream `test.py` (82 теста) сохранён без изменений; используется
`text-unidecode==1.3`. Архив исходников проверяется по SHA-256.

Два независимых режима: existing использует upstream при расчёте baseline и поиска
непокрытых строк; cold начинает с `existing_tests=()`. В обоих случаях затем
повторно запускаются созданный файл отдельно и его объединение с полным upstream.
Исходный код upstream-тестов не передаётся модели.

| Набор | Прошло тестов | Строки модуля | Ветви модуля |
|---|---:|---:|---:|
| Полный upstream, baseline | 82 / 82 | 85 / 92 = 92,39% | 46 / 50 = 92% |
| Только сгенерированные, existing | 13 / 13 | 72 / 92 = 78,26% | 30 / 50 = 60% |
| Upstream + existing | 95 / 95 | 86 / 92 = 93,48% | 47 / 50 = 94% |
| Только сгенерированные, cold | 18 / 18 | 72 / 92 = 78,26% | 34 / 50 = 68% |
| Upstream + cold | 100 / 100 | 86 / 92 = 93,48% | 47 / 50 = 94% |

В обоих режимах прирост поверх upstream — **одна строка (56), одна ветвь (55→56)**:
+1,09 процентного пункта строк, +2 п.п. ветвей. Потерянных строк и ветвей нет.
У библиотеки уже высокое покрытие; standalone 78,26% не является приростом.

| Режим | Время генерации и проверок | LLM-запросы | Токены | Отброшено тестов |
|---|---:|---:|---:|---:|
| existing | 157,2 с | 5 | 7 706 | 0 |
| cold | 130,4 с | 8 | 11 003 | 1 |

Время — один замер на GitHub runner, без статистики. В cold не удалось исправить
`test_smart_truncate_word_boundary_false`; в конечном файле его нет.
Число dropped не учитывает все отклонённые предложения: в existing в логах также есть невалидный импорт `slugify.constants` и пропуски генерации. Два свободных теста cold имеют слишком сильные названия: `max_length_equal_to_string_length` не задаёт max_length, а `word_boundary_true` оставляет max_length равным нулю и не доходит до соответствующей ветки. Их проход не доказывает заявленное именем поведение.

Оба режима выдали предупреждение для `smart_truncate` с пустым separator.
Это не подтверждённый баг библиотеки: обнаружено исключение, но нарушение контракта
из этого автоматически не следует.

[Полный отчёт](results/library-report.json) и
[архив созданных тестов, отчётов и логов](results/library-run.zip).

## 6. Воспроизведение

[Workflow](../../.github/workflows/bench-evidence.yml) закрепляет образ llama.cpp,
ревизию GGUF и архив библиотеки. Кэш ответов отключён. Суммарное время шардов в JSON
эвристики — сумма времени четырёх процессов, а не длительность параллельного workflow.
Использовано 69 запросов, 17 082 входных и 2 327 выходных токенов.

После запуска OpenAI-совместимого endpoint:

```powershell
$env:PYTESTGEN_LLM_BASE_URL = "http://localhost:8080/v1"
$env:PYTESTGEN_LLM_MODEL = "qwen2.5-coder-1.5b-instruct"
uv run --frozen python scripts/bench_heuristic.py --output out/heuristic-new.json
uv run --frozen --with text-unidecode==1.3 python scripts/bench_library.py --mode both --output out/library-new
```

В GitHub тот же скрипт запускается с `--shard N --shards 4`, затем
`--combine` проверяет полноту 32 + 32 сценариев и совпадение версий.
Фиксированный seed не гарантирует битовой воспроизводимости инференса.

Контрольные суммы и происхождение: [manifest.json](results/manifest.json).
Артефакты библиотеки содержат сгенерированные тесты и повторные прогоны отдельно
и вместе с upstream. Логи pytest — сохранённые хвосты, не полные трассы.
Промпты эвристики содержат только специально написанные публичные функции и тесты.

Ограничения: восемь заранее выбранных семейств, одна библиотека, один прогон модели,
без оценки обобщения на другие проекты. Презентация дополняет живую демонстрацию.
Публикация в main и Docker Hub остаётся отдельным этапом сдачи.

## 7. Проверка отдельных исходов

[Индекс всех 32 исправлений и 32 оценок оракула](case-index.md) позволяет найти запись
в исходном JSON по ID. У 21 неуспешного repair оба ответа сохраняют AST исходного теста:
все 42 повторных исполнения снова падают по ожидаемой причине.
Отсутствие подгонки в этих сценариях не означает сохранения теста-свидетеля:
приложение в конце отбрасывает неисправленный падающий тест.

Для python-slugify новая строка 56 — возврат с обрезкой, когда разделитель
не встречается в строке. Пример из итогового набора existing:

```python
assert smart_truncate("s", 1, True, "l", False) == "s"
```

Он имеет источник `z3`; замер показывает полезность детерминированной части
даже при уже высоком upstream-покрытии. Однако записанный результат остаётся
регрессионным ожиданием, а не независимым доказательством правильности функции.
