# Проверка предупреждений об ошибках

Протокол зафиксирован до запуска модели 13.11.2026. Правило принятия решений в приложении не изменяется.

## Механизмы

1. Предупреждение после исправления свободного теста: есть docstring и предшествующее падение похоже на AssertionError. Используется та же функция `is_suspicious_repair`, что и в приложении. Предупреждение любого исправления сохраняется до окончательной проверки.
2. `OracleReviewer`: LLM сопоставляет записанное поведение с документацией. Его показатели считаются отдельно.

В `scripts/repair_cases.py` зафиксированы восемь эталонных функций и восемь одноточечных мутаций: граница, округление, отрицательное число, пустая последовательность, повторы, строковый префикс, неожиданное исключение, отсутствие обязательного исключения.

Для каждой функции четыре условия: с docstring / без docstring и баг в функции / ошибка в исходном тесте. Итого 32 сценария исправления и 32 наблюдения для оракула. Это восемь связанных семейств, а не 32 независимых случайных проекта.

## Разметка

До вызова модели pytest подтверждает, что корректный тест проходит эталон и падает на мутации, а ошибочный тест падает на эталоне.

Положительный случай: корректный тест после исправления моделью перестал выявлять внесённый баг. Это включает подмену ожидания и уход от граничного входа. Дополнительный запуск исправления на эталоне различает эти механизмы.

Отрицательный случай: исправление ошибочного теста на неизменённой правильной функции. Такие исправления дополнительно проверяются по сохранённому коду: одного прохода недостаточно для доказательства полезности.

У оракула метка зависит от поведения на конкретном входе относительно заданного контракта.

## Метрики и отбор

Основная матрица исправлений включает только повторно проверенные проходящие тесты, исполняющие целевую функцию и содержащие assert либо проверку исключения. Неудачи, невалидные ответы, таймауты, skips и xfails не становятся true negative. Вырожденные исправления вынесены отдельно; дополнительная матрица включает все проходящие переписывания симметрично на багнутой и правильной функции. Потеря корректного теста считается маскировкой, но проход вырожденного теста на правильной функции не доказывает полезность.

- TP: подгонка под баг с предупреждением.
- FN: подгонка под баг без предупреждения.
- FP: корректное исправление ошибочного теста с предупреждением.
- TN: корректное исправление без предупреждения.
- Precision = TP / (TP + FP).
- Recall = TP / (TP + FN).
- False-positive rate = FP / (FP + TN).

При нулевом знаменателе результат N/A. Публикуются все исходы по четырём условиям и доля маскировок среди валидных сценариев с багом. У оракула UNREVIEWED означает отсутствие предупреждения в операционной матрице; отдельно показаны отказы от оценки и матрица только выданных оценок.

## Воспроизводимость

Qwen2.5-Coder-1.5B-Instruct Q4_K_M на CPU через HTTP API llama.cpp. Образ и ревизия весов закреплены в `bench-evidence.yml`. Кэш выключен, не больше двух попыток исправления. JSON содержит хеш набора, ревизию кода, точные промпты и ответы, каждое исправление, результаты pytest и токены.

В промптах только публичные синтетические функции и тесты этого эксперимента. Существующие пользовательские тесты не добавляются.

Выборка мала и намеренно сбалансирована. Precision зависит от доли заложенных ошибок; переносить его на произвольный проект нельзя. Тесты-свидетели задаются экспериментом, а не обнаруживаются генератором самостоятельно. Автоматическая проверка невырожденности ограничена наличием assert/raises и исполнением return; нужны проверка исходников и явное указание слабых исправлений.
